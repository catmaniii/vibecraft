# M1.2 设计预研：SC2 子进程生命周期管理

> Opus 预研产出（2026-05-14），趁 M1.1b-e 由 subagent 并行实现时做。
> M1.2 实现者照此落地；带 ⚠️ 的是需要先 spike 验证的未决点。
>
> 上游依据：
> - 设计文档 `2026-05-14-voicecraft-design.md` §3.3（启动时序两阶段）、
>   §9.3（`start_game` / `game_status` 帧）、§9.6（三段式状态链）

---

## 1. M1.2 要解决什么

收到手机的 `start_game` 帧 → 拉起 SC2 客户端 → 全程把启动 / 对局 / 结束 /
崩溃状态推回手机 → 游戏结束或崩溃能干净善后。

四个架构难点（下面逐个）：
1. `run_game()` 是**阻塞**调用，怎么跑而不卡死 WS server
2. SC2 启动 / 对局阶段怎么**检测**并映射到 `game_status.sc2`
3. SC2 崩溃 / `run_game` 抛异常 / 死锁 怎么**捕获上报**
4. bot service ↔ 游戏 的**双向通信通道**

```
手机 ──start_game──> WS server ──> [M1.2: GameProcess] ──run_game()──> SC2 客户端
   <──game_status──            <── 状态/事件 ────────                （独立进程/线程）
```

---

## 2. 难点 1：`run_game()` 阻塞，怎么跑

`run_game()` 同步阻塞，跑完一整局才返回（M0c smoke 验证过：`20:37:37`
进对局 → `20:38:49` 返回）。bot service 的 WS server 是 asyncio event loop ——
`run_game()` 绝不能直接在这个 loop 里跑。

| 方案 | 机制 | 优 | 劣 |
|---|---|---|---|
| **A 独立线程** | `threading.Thread` 跑 `run_game()`，线程内自建 event loop | 不需序列化，bot 对象直接共享；实现简单 | 线程没法干净 kill —— SC2 死锁 / `run_game` 卡住时线程也卡，只能整个进程退 |
| **B 独立进程** | `multiprocessing` spawn 子进程跑 `run_game()` | 隔离彻底，SC2 崩 / 卡不波及 WS server，可 `terminate()` 强杀 | ⚠️ Windows 用 spawn，跨进程参数要 picklable —— bot 对象 / director 工厂能否传过去存疑 |
| C asyncio executor | `loop.run_in_executor` | 比 A 少手动管理 | 本质还是线程，劣势同 A |

**倾向 B（独立进程）**，理由：M0c 已经踩过 SC2 客户端崩 / 文件锁，进程隔离
让 WS server 能可靠检测 + 强制善后；通信量小（都是小 JSON），序列化开销可接受。

⚠️ **但 B 有个必须先 spike 的点**：Windows 没有 `fork`，`multiprocessing` 用
`spawn` —— 子进程要重新 import 模块、传进去的参数必须 picklable。`AresBot`
子类实例、`make_bot_class` 的 director 工厂大概率**不可 pickle**。

→ **M1.2 第一步 = spike**：验证「在子进程内部构造 bot」是否可行 ——
即父进程只传 picklable 的配置（map 名 / 对手 / token / 端口），子进程
`if __name__` 入口里自己 `make_bot_class()` + `run_game()`。`scripts/smoke_test.py`
的 `main()` 其实已经是这个形态（自己 parse_args → build_bot_class → run_game），
可直接参考改造成子进程入口。spike 通过则 B 成立；不通过退回 A。

## 3. 难点 2：启动 / 对局阶段检测

python-sc2 的 `Status`，M0c smoke 日志里观察到的完整序列：

```
Status.launched → Status.init_game → Status.in_game
   ...(对局)...
→ Status.launched → Status.quit          # 游戏结束后
```

映射到设计文档 §9.3 的 `game_status.sc2` 字段：

| 阶段信号 | game_status.sc2 |
|---|---|
| 子进程已 spawn，`run_game()` 还没进对局 | `launching` |
| `Status.launched` / `init_game` | `launching` |
| ares bot 的 `on_start()` 被调用（已进对局） | `in_game` |
| `on_step()` 正常推进 | `playing` |
| `run_game()` 正常返回 / `on_end()` | `ended` |
| `run_game()` 抛异常 / 超时 / 进程非正常退出 | `crashed` |

**信号怎么拿**：
- `on_start` / `on_step` / `on_end` —— ares bot 的回调（M0c 的 `SmokeBot`
  已经用了 `on_start` / `on_step`）。在这些回调里往通信通道发阶段信号。
- `run_game()` 返回 / 抛异常 —— 进程 / 线程层面知道 `ended` / `crashed`。
- spawn 到 `on_start` 之间的窗口 = `launching`。

---

## 4. 难点 3：崩溃 / 异常捕获

`run_game()` 用 `try/except` 包（M0c `smoke_test.py` 的 `main()` 就是这么做的，
异常时 `session.log_event` + 返回非 0）。M1.2 要捕获三类：
- `run_game()` 抛异常（地图缺 / 版本不匹配 —— M0c 全踩过）
- SC2 客户端自己崩（进程退出码非 0）
- 死锁 / 无响应 —— 需要 watchdog（设计文档 §11.1 提到「watchdog 10s 判定」）

捕获后通过通信通道发 `game_status{sc2: "crashed", detail: "<具体原因>"}`，
WS server 转发给手机（设计文档 §9.6 错误分三层里的「SC2 启动层」）。

方案 B（独立进程）的额外好处：子进程异常退出，父进程 `proc.exitcode` 直接可读，
即使子进程自己来不及上报，父进程也能兜底判定 `crashed`。

## 5. 难点 4：bot service ↔ 游戏 双向通信

双向：
- **上行**（游戏 → service）：`game_status`（阶段 / 崩溃）；后续 M1.6 还有
  `snapshot` / `event`
- **下行**（service → 游戏）：`start_game` 的 config；后续 M1.4+ 有 `command`

配合方案 B：
- 进程间：两个 `multiprocessing.Queue`（上行一个、下行一个），或一个 `Pipe`
- WS server 端：一个 asyncio task 把上行 Queue 泵进 WS 推送；一个把 WS 收到的
  指令泵进下行 Queue
- ⚠️ `multiprocessing.Queue` 的 `get()` 是**阻塞**的 —— asyncio 端不能直接
  `get()`，要用 `loop.run_in_executor` 包，或用 `aioprocessing` 之类桥接库。
  别阻塞 event loop。

## 6. 接口草案（给 M1.2 实现者）

放 `src/voicecraft/server/game_process.py`（或 `game/` 子包）：

```python
class GameConfig:          # picklable，能跨进程传
    map_name: str
    opponent_race: str
    opponent_difficulty: str
    realtime: bool = True  # 玩家要看画面，默认实时

class GameProcess:
    """管一局游戏的子进程生命周期。bot service 持有一个。"""
    def start(self, config: GameConfig) -> None: ...   # spawn 子进程跑 run_game
    @property
    def status(self) -> str: ...                       # 当前 sc2 状态
    async def status_events(self) -> AsyncIterator[GameStatus]: ...  # 上行流
    def send_command(self, cmd: dict) -> None: ...     # 下行（M1.4+ 用）
    async def stop(self) -> None: ...                  # 善后：leave / terminate / join
```

WS server（M1.1b 的 stub handler）收到 `start_game` 帧 →
`GameProcess.start(config)`；`status_events()` 的流 → 包成 `game_status` 帧推手机。

## 7. 跟 M1.1 / M1.5 的衔接

- **M1.1b**（subagent 正在做）：WS endpoint 收到 `start_game` 帧时 handler 是
  **stub**。M1.2 把这个 stub 换成 `GameProcess.start()`。
- **M1.5**：`ares_adapter` 真实现 `set_build` —— 子进程里 `run_game()` 跑的
  bot 就是 `VoiceCraftBot`。**M1.2 管它的进程外壳，M1.5 管它内部的能力**。
  两者通过难点 4 的下行通道衔接（command → directive → facade）。

   picklable config、子进程自己构造 bot」（见 §2）。决定 B 还是退回 A。

3. SC2 启动超时阈值（设计文档 §11.1 提 watchdog 10s，启动可能要更长 ——
   M0c 观察 SC2 冷启动到进对局约 5-6 秒，留足余量）。
4. `run_game()` 是否有比同步入口更友好的异步入口可用（待 ares 环境恢复后
   读 `sc2/main.py` 确认 —— 当前 ares 全家桶被 `uv sync` 清了，见 TASKS.md
   待办「根治 ares 依赖隐患」）。
5. 单测策略：`GameProcess` 不实际拉 SC2 —— 用 fake 子进程入口（一个不 import
   ares、只按协议吐 `game_status` 的桩）测生命周期 / 通信 / 善后逻辑。真实
   拉 SC2 归 `tests/e2e/`（default 跳过）。
