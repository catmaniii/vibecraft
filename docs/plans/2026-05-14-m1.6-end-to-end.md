## 3. 五个串通 gap

### Gap 1：子进程 bot 统一
`game_process.py._child_entry` 现在调 `_build_bot_class()` 造 `_M12Bot` stub。
M1.6 要改成调 `ares_adapter.make_bot_class(director_factory, strategy_library)`
造真 `_VibeCraftBot`。

约束（M1.2 spike 结论）：bot 必须**在子进程内构造**（`AresBot` 子类不可
pickle）。所以 `director_factory` / `strategy_library` 也要在子进程内构造 ——
`_child_entry` 里 `import` + 装配，父进程只传 picklable 的 `GameConfig`。

### Gap 2：下行 command Queue 激活
- WS `_dispatch` 的 `command` handler：stub → `self._game_process.send_command(
  {"type": "command", "text": <玩家话语>, "issued_at": <ts>})`（`send_command`
  M1.2 已实现，put 到 `_down_q`）
- `_child_entry` 把 `_down_q` 传给 bot（现在带下划线没传给 `_build_bot_class`）
- 子进程 `_VibeCraftBot.on_step` 里非阻塞消费 `_down_q`（`get_nowait`，空就跳过）

### Gap 3：⚠️ `on_player_command` 是 async，怎么在 `on_step` 里调而不卡游戏
`Director.on_player_command(text, now)` 是 `async`，内部 `IntentParser.parse`
要调云端 LLM —— 可能几秒（设计文档 §7.5 超时 3s）。ares bot 的 `on_step` 也是
`async`，但如果 `await director.on_player_command(...)`，**这个 step 会阻塞
几秒**，realtime 模式下游戏卡住。

**方案**：`on_step` 里 **不 `await`**，用 `asyncio.create_task(
director.on_player_command(text, now))` fire-and-forget。parse 在后台跑，完成后
directive 进 Board；下一个 `on_step` 的 `director.on_tick(now)` 会处理 Board →
facade。设计文档 §11.2 的「1.5s commit delay」天然支持这个异步链 —— directive
本来就不是立即生效。

⚠️ spike 点：确认 ares `on_step` 里 `create_task` 的 task 生命周期 —— task 要
有引用（防 GC）、要在 bot 上挂个 list 收集、异常要被捕获 log（不能让后台 task
的异常静默丢失）。

### Gap 4：ParseContext / GameSession 在子进程构造
- `Director` 要 `GameSession`（日志，`logs/<game_id>/`）—— 子进程内构造
- `IntentParser.parse` 要 `ParseContext` —— `Director.build_parse_context(now)`
  已实现，从 `facade.get_state()` 拿 game state（facade 是 M1.5 的 `_AresFacade`，
  子进程内已有）。这条已通，无需新代码。
- M1.4 的 LLM 全量日志（`llm_calls/call_NNN.json`）也落子进程的 `GameSession`

### Gap 5：状态推送 hook（真 bot 也要推 game_status）
`_M12Bot` stub 的价值是 `on_start/on_step/on_end` 往上行 Queue 推
`in_game`/`playing`/`ended`。换成真 `_VibeCraftBot` 后，这个推送逻辑不能丢。
方案：`make_bot_class` 增加一个可选的 `status_callback` 参数（或让
`_child_entry` 把 `_put` 闭包传进去），真 bot 的 `on_start/on_step/on_end`
里调它推状态。

## 4. 串通后的端到端链路

```
手机说话
  → PWA command 帧（M1.3 已就绪）
  → WS server _dispatch（Gap 2：stub → send_command）
  → GameProcess._down_q（Gap 2：激活）
  → 子进程 _VibeCraftBot.on_step 消费 _down_q（Gap 1+2）
  → asyncio.create_task(director.on_player_command(text, now))（Gap 3：不阻塞）
       ↓（后台）
     IntentParser.parse → directives → board.submit
  → 下一个 on_step：director.on_tick(now) → board.tick → COMMITTED
  → facade.set_build("1g_robo_immortal")（M1.5 已就绪）
  → ares build_order_runner.switch_opening(...)
  → SC2 真的切 build
```

## 5. 范围边界

- **M1.6 出口聚焦「指令真的生效」** —— 手机说「切1门Robo」→ SC2 切 build。
- **echo / 反馈做基础版**：设计文档 §9.3 有 `echo`（「我理解为 X」+ 1.5s 撤销）。
  M1.6 至少做一个**基础 echo 上行**（让玩家知道指令收到了 + 解析结果），
  但完整的撤销按钮 / pending_echo 计时器是 M3 驾驶舱的事。
- **不做**：snapshot 完整推送、minimap、view 控制、unit_claim 那些 —— 它们的
  directive 类型 M0b 都有，但端到端验证 M1.6 只需打通 `strategy_set` 这一条。
- 真实 SC2 验证需要用户在场（设计文档「工作模式」：到必须真实启动 SC2 才喊人）。

## 6. M1.6 实现者的 spike / 待办

1. ⚠️ **spike**：ares `on_step` 里 `asyncio.create_task` 的 task 管理 —— 引用
   保持（防 GC）、异常捕获 log、bot 退出时清理未完成 task。
2. `_child_entry` 的子进程装配：在子进程内 import + 构造 GameSession /
   StrategyLibrary / AnthropicProvider / IntentParser / director_factory。注意
   `ANTHROPIC_API_KEY` 环境变量子进程能否继承（spawn 子进程继承父进程 env，
   应该可以，spike 确认）。
3. `make_bot_class` 扩展：加 `status_callback` + `down_q` 参数（Gap 1+5）。
   保持 `strategy_library=None` / 这俩 =None 时的向后兼容（M0c smoke 仍能跑）。
4. WS `_dispatch` 的 `command` handler：stub → `send_command`。
5. 基础 echo：子进程 parse 完 → 上行 Queue 推一条 echo 消息 → WS → 手机。
   上行 Queue 现在传 `game_status`，要扩展成能传多种消息类型（加 `kind` 字段）。
6. 单测：串通逻辑尽量单测（mock down_q / mock director）；真实 SC2 跑是
   `tests/e2e/`（default skip）+ 用户手测。
7. **真实验证清单**（给用户）：启 bot service → 手机扫码 → 点开始对局 →
   说「切1门Robo」→ 看 SC2 是否切到 `1g_robo_immortal` build。需
   `ANTHROPIC_API_KEY`（M1.4 的真实 API 验证也在这一步一起做了）。
