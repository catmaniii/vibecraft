### 0.3 bot 取小地图数据：python-sc2 / ares 端可行性确认

| 需要 | 来源 | 类型 |
|---|---|---|
| 地图世界尺寸（pathing grid 尺寸） | `bot.game_info.map_size` | `Size`（NamedTuple `(width, height)`，整数 tile，常见 144×136 / 168×168）|
| **可玩区域**（minimap 实际显示这一块）| `bot.game_info.playable_area` | `Rect(x, y, width, height)`（playable bounds，比 map_size 内缩一圈不可达边缘）|
| start_locations / player_start_location | `bot.game_info.start_locations` / `player_start_location` | `List[Point2]` / `Point2` |
| **当前 player 相机中心** | `bot.state.observation_raw.player.camera` | proto `Point`，`.x .y` 取（**已被 ares 自己用过**：`src/ares/chat_debug.py:140`）|
| 己方单位 | `bot.units` / `bot.structures` / `bot.townhalls` | `Units`（list of Unit），`.position_tuple` 取 (x,y) |
| 敌方可见单位 | `bot.enemy_units` / `bot.enemy_structures` | `Units`；`.is_visible` 区分实时可见 vs fog 记忆 |

**结论**：viewport 矩形可以从 `observation_raw.player.camera` 真实得到，无需"估算"。
camera 字段是当前 player 视野中心（世界坐标），SC2 大屏的视野矩形宽高约
24 × 18（世界单位）—— 这是 SC2 引擎硬编码的标准 RTS 视角；MVP 用固定 (24,18) 估算
viewport 矩形足够（spike S3 验证）。

## 1. minimap 帧最小实现

### 1.1 MVP 推什么字段

设计文档 §9.3 的完整 `minimap` 帧定义了 `viewport / units_own / units_enemy_visible` 
三块。MVP 全部都推但**字段取最小子集**：

```jsonc
// 下行帧：minimap —— MVP 子集
{
  "type": "minimap",
  "ts": 332.4,                       // 游戏内秒 float(bot.time)
  "map": {                           // 静态地图元信息（每帧重复推，几十字节，可承受）
    "playable": [16, 12, 152, 116],  // [x, y, w, h]：playable_area，世界坐标
    "size": [168, 168]               // 完整 map_size（pathing grid 尺寸），辅助调试
  },
  "viewport": {
    "center": [88.5, 134.2],         // observation_raw.player.camera.{x,y}
    "size":   [24, 18]               // SC2 大屏视角硬编码估算（spike S3 验证）
  },
  "units_own": [                     // 己方所有单位（含建筑）
    [88.0, 130.5, "P"],              // [x, y, kind] —— kind 一字节区分形状/颜色
    [85.0, 132.0, "S"],
    ...
  ],
  "units_enemy_visible": [           // 敌方"当前可见"（is_visible == true）
    [42.5, 96.0, "?"],               // MVP 不区分敌方兵种，统一 "?"
    ...
  ]
}
```

字段决策理由：

- **`map.playable`**：每帧重发是冗余（playable_area 整局不变）。但 MVP 不另开"地图静态
  元信息帧"省一类协议 —— 一个矩形 4 个 int = ~30 字节/帧，可接受。M3 可优化成
  `snapshot` 首发一次 + minimap 不重复（写在 §6 优化清单）。
- **`viewport.size`**：固定 `[24, 18]` 是估算，SC2 大屏 16:9 视角实际窗高/宽因屏幕分辨率
  会变（python-sc2 不直接暴露），MVP 这个值够"画一个看着像"的矩形。详见 spike S3。
- **`units_own[i] = [x, y, kind]`**：tuple 比 dict 省 50% 字节（JSON 里 `[1,2,"P"]` vs 
  `{"x":1,"y":2,"k":"P"}`）。kind 单字符枚举：
  - `"N"` = Nexus / 基地
  - `"P"` = 探机
  - `"B"` = 其它建筑（统一一类，MVP 不细分）
  - `"A"` = 战斗单位（统一一类，MVP 不区分追猎/叉子/不朽）
  - `"W"` = 工人（敌方阵营时区分工人/兵，方便玩家看骚扰）
  - 敌方一律 `"?"`（is_visible == true 才推；fog 记忆里的不推 —— 那是 M3 的事）。
- **不推单位 tag**：MVP 不做"点单位选中"。tag 是 uint64，加上一倍字节量，先省。
  M3 做单位 follow / 点选时再加。
- **不推单位 hp / shield / cooldown**：MVP 不做血量条；只是地图点。

带宽估算（典型一局中后期）：
- 单位总数 ≈ 60-80 己方 + 30-50 敌方可见 = 100-130 个点
- 每点 ≈ 14 字节（`[88.5,134.2,"P"]` JSON 形态）
- 一帧 ≈ 130 × 14 + 头部 ≈ **2 KB**
- 5 Hz × 2 KB = **10 KB/s** = 80 kbps —— LAN/局域网 WiFi 完全无压力，远低于 cockpit-sync
  现有 snapshot 2s 一发的负载。

### 1.2 谁产出：子进程 bot 内新增 MinimapBuilder

放在 `src/voicecraft/bot/`，跟 director / facade / ares_adapter 同级：

**新文件 `src/voicecraft/bot/minimap.py`**（~80 行）：
```python
class MinimapBuilder:
    """从 bot 状态构造 minimap 帧 dict。

    MVP 子集：playable / size / viewport / units_own / units_enemy_visible。
    每帧字段策略详见 docs/plans/2026-05-15-minimap.md §1.1。
    """

    def __init__(self, bot: Any) -> None:  # AresBot, 但用 Any 避免顶层 import
        self.bot = bot
        # 静态部分缓存（on_start 之后才可访问 game_info）
        self._playable: list[int] | None = None
        self._map_size: list[int] | None = None

    def _ensure_static_cached(self) -> None:
        if self._playable is None:
            pa = self.bot.game_info.playable_area
            self._playable = [int(pa.x), int(pa.y), int(pa.width), int(pa.height)]
            self._map_size = [int(self.bot.game_info.map_size[0]),
                              int(self.bot.game_info.map_size[1])]

    def build(self, now: float) -> dict[str, Any]:
        self._ensure_static_cached()
        cam = self.bot.state.observation_raw.player.camera  # proto Point
        units_own = self._collect_own()
        units_enemy = self._collect_enemy_visible()
        return {
            "type": "minimap",
            "ts": round(now, 3),
            "map": {"playable": self._playable, "size": self._map_size},
            "viewport": {
                "center": [round(cam.x, 2), round(cam.y, 2)],
                "size": [24, 18],  # spike S3
            },
            "units_own": units_own,
            "units_enemy_visible": units_enemy,
        }

    def _collect_own(self) -> list[list[Any]]:
        out: list[list[Any]] = []
        # 基地
        for u in self.bot.townhalls:
            x, y = u.position_tuple
            out.append([round(x, 1), round(y, 1), "N"])
        # 探机（is_worker 判断走 self.workers）
        for u in self.bot.workers:
            x, y = u.position_tuple
            out.append([round(x, 1), round(y, 1), "P"])
        # 其它建筑（structures - townhalls）
        for u in self.bot.structures:
            if u.tag in {h.tag for h in self.bot.townhalls}:
                continue
            x, y = u.position_tuple
            out.append([round(x, 1), round(y, 1), "B"])
        # 战斗单位（units - workers）
        worker_tags = {w.tag for w in self.bot.workers}
        for u in self.bot.units:
            if u.tag in worker_tags:
                continue
            x, y = u.position_tuple
            out.append([round(x, 1), round(y, 1), "A"])
        return out

    def _collect_enemy_visible(self) -> list[list[Any]]:
        out: list[list[Any]] = []
        for u in self.bot.enemy_units:
            if not u.is_visible:
                continue
            x, y = u.position_tuple
            # 简单工人识别：UnitTypeId.PROBE/SCV/DRONE。否则 "?"
            kind = "W" if u.type_id.name in {"PROBE", "SCV", "DRONE"} else "?"
            out.append([round(x, 1), round(y, 1), kind])
        for u in self.bot.enemy_structures:
            if not u.is_visible:
                continue
            x, y = u.position_tuple
            out.append([round(x, 1), round(y, 1), "?"])
        return out
```

复用现有 cockpit-sync 的 callback 透传链：在 `ares_adapter.make_bot_class` 加
`minimap_callback` 参数；`_VoiceCraftBot` 在 `on_start` 后构造一个 `MinimapBuilder`
持有 `self`；`on_step` 里按频率调 `minimap_callback(builder.build(self.time))`。

### 1.3 多频繁：每 N tick 推 + 心跳兜底

**采用：每 N tick 推（基于 game tick，不基于 wall clock）**。

| 方案 | 代价 | 结论 |
|---|---|---|
| A. wall clock 5 Hz（asyncio.sleep）| 要起异步任务，跟 on_step 同步状态有竞态 | ✗ |
| B. 每 N tick（on_step 内计数）| 简单，无并发；realtime 下 ~22.4 tick/s，N=5 ≈ 4-5Hz | ✓ **采用** |
| C. 状态变化推 | 单位每 tick 都在移动，本质就是高频，"变化触发"没意义 | ✗ |

具体：`_VoiceCraftBot._minimap_tick_count` 计数，`on_step` 每 5 tick 调一次 build + push。
realtime ~22.4 tick/s → 实际约 4.5 Hz，对齐 §9.3 "5Hz"。

**N 取值实操**：cockpit-sync `DirectorConfig.snapshot_interval_ticks = 45`（~2s）已经
跑过 spike，realtime tick 速度是已知的 ~22.4 Hz；minimap 取 N=5 安全。把 N 做成
`MinimapConfig.tick_interval: int = 5` 的可调字段，调优余地留出来。

**无需兜底心跳**：minimap 本身就是高频，不像 snapshot 那种"状态稳定时也要让前端有数据"。
重连后下一帧（200ms 内）就刷新，可接受。

### 1.4 上行 view_move 频率限制

玩家拖小地图会狂发 view_move 帧。三层限频：

1. **前端节流**：拖拽事件触发后，每 100ms 才发一次 view_move（pointermove 在
   `requestAnimationFrame` 节流 + 距离阈值，详见 §4.4）。即使 60fps 拖也只发 10Hz。
2. **down_q 容量**：multiprocessing.Queue 默认无界，但 view_move 帧 dict 极小（几十字节）
   且子进程 on_step 每 tick 都在 drain（`while True: down_q.get_nowait()`），不会积压。
3. **facade 层无限频**：设计文档 §9.3 明确 "view_move 不限频"。bot 侧消费即调 
   `client.move_camera`，由 SC2 protobuf 协议层自己处理。

async def _handle_view_move(self, frame: dict[str, Any]) -> None:
    """收到 view_move 帧 → 校验 → 经 down_q 发到子进程。
    
    若 SC2 对局未在 playing 状态，静默丢弃。
    """
    pt = frame.get("target_point")
    if (not isinstance(pt, list) or len(pt) != 2 
        or not all(isinstance(v, (int, float)) for v in pt)):
        self._log.warning("ws_view_move_bad_point", frame=frame)
        return
    if not self._game_process.is_running:
        self._log.debug("ws_view_move_no_game_running")
        return
    self._game_process.send_command({
        "type": "view_move",
        "target_point": [float(pt[0]), float(pt[1])],

### 2.4 ⚠️ 修复 _AresFacade.move_camera 的 async 问题（spike S1，**必修**）

§0.2 已说明：`bot.client.move_camera` 是 async 协程，当前 facade 同步姿势调它**等于
没调**。两种修法：

**方案 A**：在 facade 里 fire-and-forget 起任务
```python
def move_camera(self, point: tuple[float, float]) -> None:
    from sc2.position import Point2
    import asyncio
    coro = self.bot.client.move_camera(Point2(point))
    task = asyncio.create_task(coro, name=f"move_camera-{point}")
    # 不 await：on_step 已经在 event loop 里，view_move 不阻塞下一 tick
    task.add_done_callback(_log_move_camera_done)  # 异常时 log
```

**方案 B**：把 facade.move_camera 改成 async，调用方一路 async 上去
- _dispatch_view 改 async（director.py 里已经是 sync 函数，调用链上去会蔓延）

## 3. bot 怎么拿小地图数据：spike 确认结果

§0.3 已经把可行性查清楚了。落地细节：

### 3.1 单位坐标

`bot.units / structures / townhalls / workers / enemy_units / enemy_structures` 
都是 `Units`（list-like）。每个 `Unit` 有：
- `u.position_tuple: tuple[float, float]` → 直接取 (x, y)，避免 Point2 实例化开销
- `u.tag: int` → MVP 不用，M3 follow_unit 时用
- `u.type_id: UnitTypeId` → `u.type_id.name` 字符串（"PROBE" / "ZEALOT" / ...）
- `u.is_visible: bool` → 敌方单位用：True = 当前在视野里；False = fog 中的"上次看到的位置"
  - MVP 只推 `is_visible == True` 的敌方单位（M3 再做 fog 记忆显示）

### 3.2 地图尺寸 / playable area

- `bot.game_info.map_size: Size` —— NamedTuple `(width, height)`，可 `[0] [1]` 索引
  也可 `.width .height`
- `bot.game_info.playable_area: Rect` —— `.x .y .width .height`（左下角 + 宽高），世界坐标
- `bot.game_info.map_center: Point2` —— playable_area 中心，调试用

minimap 渲染应基于 **`playable_area`**，不是 `map_size`：map_size 是 pathing grid 全尺寸
（含不可达边缘），SC2 大屏小地图实际显示的是 playable_area。

### 3.3 当前 camera 中心：observation_raw.player.camera

```python
cam_proto = self.bot.state.observation_raw.player.camera   # s2clientprotocol Point
cx, cy = cam_proto.x, cam_proto.y
```

**ares 自己用过这个写法**（`.venv/Lib/site-packages/src/ares/chat_debug.py:140`）：
```python
player_camera = self.ai.state.observation_raw.player.camera
pos = Point2((player_camera.x, player_camera.y))
```
→ 可放心用，不需要 spike 验证字段存在性。

### 3.4 viewport size 估算

python-sc2 / ares 都**不直接暴露 SC2 大屏当前视野矩形宽高** —— camera 字段只给中心
点，视野范围由 SC2 引擎内部根据屏幕分辨率算。

MVP 用固定值 `[24, 18]`：SC2 标准 16:9 视角下世界单位约 24×18。**spike S3** 验证：
开局 SC2 起来后，把 cam.x cam.y 和肉眼看到的 SC2 视野矩形对比，调整这个固定值到"看着
合理"为止（可能在 20-28 / 14-20 区间）。

如果 spike S3 发现固定值视角不准，**有 fallback**：让 viewport size **跟随上一次
玩家 view_move 的 target_point** 计算（玩家拖完，bot 回应 client.move_camera 后
下一帧 camera 字段会 == target_point；显示矩形以 target_point 为中心、固定 24×18 大小
即可）。本质上玩家自己拖出来的 viewport 看起来就和实际 SC2 视野一致。

## 4. 前端 Minimap.vue 组件

### 4.1 Canvas vs SVG：选 Canvas

| 方案 | DOM 节点数（130 单位 + viewport） | 5Hz 重渲染 | 拖拽响应 | 结论 |
|---|---|---|---|---|
| SVG（每单位一个 `<circle>` / `<rect>`） | ~150 个 DOM 节点；每帧全替换 → Vue 响应式 + 浏览器布局 reflow | **5Hz × 150 nodes 移动端会卡** | rAF 内多次 reflow | ✗ |
| Canvas（一张 `<canvas>`，每帧 clearRect + redraw） | 1 个节点；纯绘图，不触发布局 | 130 个 fillRect ≈ <2ms | rAF 拖拽流畅 | ✓ **采用** |

> 实测参考：移动端 Chrome 5Hz × 100 SVG nodes 大约 30-50ms/帧；同样负载 Canvas <5ms/帧。
> 设计文档 §9.1 也明确 "渲染: HTML5 Canvas (小地图)"。

### 4.2 组件骨架

**新文件 `web/src/components/Minimap.vue`**：

```vue
<script setup lang="ts">
import { ref, watch, onMounted, onUnmounted } from 'vue'
import type { MinimapFrame } from '@/types'

const props = defineProps<{
  frame: MinimapFrame | null
}>()

const emit = defineEmits<{
  viewMove: [point: [number, number]]
}>()

const canvas = ref<HTMLCanvasElement | null>(null)
const CANVAS_W = 280  // dp，§9.5
const CANVAS_H = 280

// 世界坐标 ↔ canvas 像素坐标
function worldToCanvas(wx: number, wy: number, playable: number[]): [number, number] {
  const [px, py, pw, ph] = playable
  // playable_area 是世界坐标矩形；映射到 canvas 时 y 轴翻转（SC2 y 向上，canvas y 向下）
  const cx = ((wx - px) / pw) * CANVAS_W
  const cy = CANVAS_H - ((wy - py) / ph) * CANVAS_H
  return [cx, cy]
}

function canvasToWorld(cx: number, cy: number, playable: number[]): [number, number] {
  const [px, py, pw, ph] = playable
  const wx = (cx / CANVAS_W) * pw + px
  const wy = ((CANVAS_H - cy) / CANVAS_H) * ph + py
  return [wx, wy]
}

function render(f: MinimapFrame) {
  const ctx = canvas.value?.getContext('2d')
  if (!ctx) return
  ctx.clearRect(0, 0, CANVAS_W, CANVAS_H)

  // 背景
  ctx.fillStyle = '#1a1a2e'
  ctx.fillRect(0, 0, CANVAS_W, CANVAS_H)

  // playable area 边框
  ctx.strokeStyle = '#444'
  ctx.lineWidth = 1
  ctx.strokeRect(0, 0, CANVAS_W, CANVAS_H)

  const pl = f.map.playable
  // 己方单位
  for (const [x, y, k] of f.units_own) {
    const [cx, cy] = worldToCanvas(x, y, pl)
    ctx.fillStyle = k === 'N' ? '#4a9eff' : k === 'P' ? '#a0c8ff' :
                    k === 'B' ? '#2a6eef' : '#4a9eff'   // 战斗单位
    const r = k === 'N' ? 4 : k === 'B' ? 3 : 2
    ctx.fillRect(cx - r/2, cy - r/2, r, r)
  }

  // 敌方可见
  for (const [x, y, k] of f.units_enemy_visible) {
    const [cx, cy] = worldToCanvas(x, y, pl)
    ctx.fillStyle = k === 'W' ? '#ff8080' : '#ff3030'
    ctx.fillRect(cx - 1, cy - 1, 2, 2)
  }

  // viewport 矩形
  const [vx, vy] = worldToCanvas(
    f.viewport.center[0], f.viewport.center[1], pl,
  )
  const vw = (f.viewport.size[0] / pl[2]) * CANVAS_W
  const vh = (f.viewport.size[1] / pl[3]) * CANVAS_H
  ctx.strokeStyle = '#ffea00'
  ctx.lineWidth = 1.5
  ctx.strokeRect(vx - vw/2, vy - vh/2, vw, vh)
}

watch(() => props.frame, (f) => f && render(f))

// 拖拽：pointerdown / move / up 统一手势（touch + mouse 都触发 pointer 事件）
let dragging = false
let lastSentMs = 0
const THROTTLE_MS = 100

function onPointerDown(e: PointerEvent) {
  dragging = true
  canvas.value?.setPointerCapture(e.pointerId)
  // 立即响应：单击也算"切到这个点"
  sendIfChanged(e)
}

function onPointerMove(e: PointerEvent) {
  if (!dragging) return
  const now = performance.now()
  if (now - lastSentMs < THROTTLE_MS) return
  sendIfChanged(e)
  lastSentMs = now
}

function onPointerUp(e: PointerEvent) {
  if (!dragging) return
  dragging = false
  canvas.value?.releasePointerCapture(e.pointerId)
  // 抬起时再发一次（节流可能漏掉终点）
  sendIfChanged(e)
}

function sendIfChanged(e: PointerEvent) {
  if (!canvas.value || !props.frame) return
  const rect = canvas.value.getBoundingClientRect()
  const cx = e.clientX - rect.left
  const cy = e.clientY - rect.top
  // 钳到 canvas 范围内（拖出去也算最近边缘）
  const ccx = Math.max(0, Math.min(CANVAS_W, cx))
  const ccy = Math.max(0, Math.min(CANVAS_H, cy))
  const [wx, wy] = canvasToWorld(ccx, ccy, props.frame.map.playable)
  emit('viewMove', [wx, wy])
}
</script>

<template>
  <div class="rounded-lg overflow-hidden border border-border bg-surface-3">
    <canvas
      ref="canvas"
      :width="CANVAS_W"
      :height="CANVAS_H"
      class="block touch-none select-none w-full"
      @pointerdown="onPointerDown"
      @pointermove="onPointerMove"
      @pointerup="onPointerUp"
      @pointercancel="onPointerUp"
    />
    <p v-if="!frame" class="text-xs text-muted italic text-center py-2">
      等待小地图数据...
    </p>
  </div>
</template>
```

要点：
- `touch-none` Tailwind class 关掉浏览器默认 touch 行为（不让"拖小地图"被浏览器解释成
  滚页面 / 缩放）
- `setPointerCapture`：手指 / 鼠标拖出 canvas 后仍跟随
- `pointerdown / pointermove / pointerup` 同一套代码处理 touch + 鼠标 + 笔（pointer events
  是统一抽象）
- 100ms 节流 + pointerup 兜底发末点 = 拖拽时上行 view_move 最多 ~10Hz，down_q 完全
  不会卡（§1.4）

### 4.3 坐标变换 / y 轴翻转

SC2 世界坐标 y 轴向上（playable_area.y 是底边）；HTML canvas y 轴向下。映射时翻转：
- `cy = CANVAS_H - (wy - py) / ph * CANVAS_H`
- 反向：`wy = (CANVAS_H - cy) / CANVAS_H * ph + py`

playable_area 不是 [0,0,map_w,map_h] —— 一般 (16,12,152,116) 这种内缩矩形。Minimap.vue
全靠 `f.map.playable` 算映射，不依赖 map_size。

### 4.4 拖拽频率限制（§1.4 落地）

- `THROTTLE_MS = 100`：相邻两次 view_move 至少间隔 100ms
- 单击（pointerdown 立即发）+ 拖拽（节流到 10Hz）+ pointerup 末点（兜底）= 一次拖拽
  典型发 3-8 帧
- **不在 client 层做空间阈值**（"移动 < 1px 不发"）：拖拽起点和终点用户预期是精确控制，
  阈值会让微调失灵

                      | EventFrame | CommandEchoFrame | MinimapFrame
export type UpFrame = StartGameFrame | CommandFrame | ViewMoveFrame

### 6.2 useWs.ts 加 minimap 处理

```ts
// 内部 ref
const minimap = ref<MinimapFrame | null>(null)

// onmessage switch 加 case
case 'minimap': {
  minimap.value = frame as MinimapFrame
  break
}

// 便捷上行函数
function sendViewMove(point: [number, number]) {
  send({ type: 'view_move', target_point: point })
}

// 返回值加
return {
  ...,
  minimap: readonly(minimap),
  sendViewMove,
}
```

## 7. 分阶段建议

**结论：一起做（小地图显示 + 拖拽切视野同一里程碑交付），不拆 P0/P1**。

理由：

| 拆分方案 | 代价 | 结论 |
|---|---|---|
| A. 一起做（minimap 帧 + view_move + 架子重排）| 单里程碑改 6 个文件 + 3 个新组件，但全部互相强依赖 | ✓ **采用** |
| B. P0 单向（minimap 显示）+ P1 拖拽 | 后端管线（_dispatch_upstream minimap 分支）是 P0 ；view_move 是 P1。但前端 Minimap.vue 在 P0 阶段不带拖拽就只是个"摆设"，独立验证价值低 | ✗ |
| C. 先架子重排 + 占位，再 minimap + view_move | 占位阶段先发个版本验证布局不破现有功能；再做核心。**有价值** | 可选 |

**推荐节奏**（同里程碑内的步骤顺序，不是阶段拆分）：

1. **Step 1（小，~半天）**：架子重排 + M3Placeholder 组件 + Minimap.vue **空壳**
   （只显示 "等待小地图数据..."）。验证：现有功能（剧本卡片 / 决策流 / 输入）不被破坏。
2. **Step 2（必跑 spike，~1-2 小时）**：S1 修 `_AresFacade.move_camera` 的 async 问题；
   smoke 跑一次确认 SC2 大屏视野**真的能被命令移动**。这是整条链路的"地基"，必须先验。
3. **Step 3（中，~半天 + spike S3）**：minimap 帧端到端打通 —— MinimapBuilder +

4. **Step 4（中，~半天）**：view_move 端到端打通 —— Minimap.vue 拖拽 + sendViewMove +

   确认手机拖一下 SC2 大屏切视野。

**总工作量估算**：~2-3 个开发日 + spike 验证。

### 不在本里程碑（划界）
