## 1. 核心发现：M0b 骨架的假设是错的

`src/vibecraft/bot/ares_adapter.py` 当前 `set_build` 写的是：

```python
def set_build(self, build_name: str) -> None:
    self.bot.build_runner.set_build(build_name)   # ← 全错
```

实读 ares 源码，三处都不对：
1. AresBot 的属性叫 **`build_order_runner`**，不是 `build_runner`
2. `BuildOrderRunner` **没有 `set_build()` 方法**
3. 切换 build 的真实方法是 **`switch_opening(opening_name)`**，且 `opening_name`
   **必须预先存在于 `bot.config["Builds"]` 里**（`configure_opening_from_yml_file`
   里有 `assert opening_name in config[BUILDS]`）

这正是 M0c runbook §4 预告的「实际 ares API 名要端到端校准」。M1.5 不是「填一行」，
是要补一个**翻译层 + 启动注入**。

## 2. ares build runner 真实 API

### BuildOrderRunner（`build_order_runner.py`）

```python
# AresBot.on_start 时构造（main.py:332）：
self.build_order_runner = BuildOrderRunner(
    self,                                          # ai
    self.manager_hub.data_manager.chosen_opening,  # str，初始 opening 名
    self.config,                                   # dict，含 "Builds" key
    self.manager_hub.manager_mediator,
)

# 关键方法：
def switch_opening(self, opening_name: str, remove_completed: bool = True) -> None
    # 切到 config["Builds"][opening_name]；remove_completed=True 会跳过已完成的步骤
@property
def build_completed -> bool          # 一个 opening 跑完后 True，run_build 不再跑
@property
def chosen_opening -> str            # 当前 opening 名
```

ares 每个 `on_step` 调 `build_order_runner.run_build()`（`main.py:393`，
仅当 `not build_completed`）。**一个 opening 跑完就停** —— 见 §5 范围边界。

### config 结构（ares `consts.py`：`BUILDS="Builds"` / `OPENING_BUILD_ORDER="OpeningBuildOrder"`）

```yaml
Builds:
  <opening_name>:
    OpeningBuildOrder:
      - "<step string>"
      - ...
    AutoSupplyAtSupply: 200          # 可选
    ConstantWorkerProductionTill: 0  # 可选
    PersistentWorker: true           # 可选
    ShouldHandleGasSteal: true       # 可选
```

### ares step 字符串格式

`BuildOrderParser.parse(raw: list[str])` 逐条解析。每条是
`"<supply> <command> [args]"`。`<command>` 两类：
- **语义命令**（`BuildOrderOptions` 枚举）：`supply` / `gas` / `expand` /
  `worker` / `worker_scout` / `overlord_scout` / `chrono` / `orbital` /
  `cancel_gas` / `addonswap`
- **直接的结构 / 单位 / 升级名**：如 `gateway` / `immortal` / `warpgateresearch`

例：`"21 addonswap factory barracksreactor"`、`"13 supply"`、`"14 gateway"`

## 3. 核心架构 gap：vibecraft 剧本 ≠ ares builds

| | vibecraft 剧本（`strategies/protoss/*.yaml`） | ares builds |
|---|---|---|
| 格式 | 自有 schema：`kind` / `id` / `phases` / `steps` / `abort_signals` / ... | `config["Builds"][name]["OpeningBuildOrder"]` |
| step | `"<supply> <verb> <object> [@modifier]"` | `"<supply> <command> [args]"` |
| verb | `build` / `research` / `train` / `send_probe` | 语义命令 or 直接名 |

### step 翻译映射（vibecraft → ares）

| vibecraft step | ares step | 说明 |
|---|---|---|
| `13 build Pylon` | `13 supply` | Pylon = 神族 supply，ares 有 `supply` 语义命令 |
| `14 build Assimilator` | `14 gas` | ares 有 `gas` 语义命令 |
| `20 build Nexus` | `20 expand` | ares 有 `expand` 语义命令 |
| `14 build Gateway` | `14 gateway` | 普通结构 → 直接小写结构名 |
| `17 build CyberneticsCore` | `17 cyberneticscore` | 同上 |
| `24 build RoboticsFacility` | `24 roboticsfacility` | 同上 |
| `22 research WarpGateResearch @chrono` | `22 warpgateresearch` + 插一条 `22 chrono` | `@chrono` modifier → ares 单独的 `chrono` step |
| `32 train Observer` | `32 observer` | 单位 → 直接小写单位名 |
| `34 train Immortal` | `34 immortal` | 同上 |
| `scout_at: "17 send_probe enemy_natural"` | `17 worker_scout` | ares 有 `worker_scout` 语义命令 |

⚠️ **spike 点**：`build Pylon` 该翻成 `supply`（语义命令）还是 `pylon`（直接名）？
ares `_parse_string_command` 对两者的处理可能不同（语义命令带 start/end
condition，直接名走通用路径）。M1.5 实现者先 spike 确认 ares 对 protoss
supply / gas / expand 的偏好。其余普通结构 / 单位用「直接小写名」应该稳。

## 4. M1.5 方案：翻译层 + 注入 config + switch_opening

三步：

### 4.1 翻译层
`src/vibecraft/bot/` 或 `strategy/` 下新增 `ares_build_translator.py`（命名实现者
定）：把一个 vibecraft `opening_build` 剧本翻成 ares 的
`{"OpeningBuildOrder": [...], ...}` dict。核心是 §3 的 step 映射 + verb/object
映射表。vibecraft 的 `phases` / `abort_signals` / `default_transitions` 在
M1.5 **不翻译**（ares build runner 不认这些；它们归 vibecraft 自己的 Directive
Board / DSL 处理，是 M2+ 的事）。

### 4.2 启动时注入 ares config
`ares_adapter` 的 bot 类在 `on_start`（或更早）把 vibecraft 所有
`opening_build` 剧本（M1.5 至少 `1g_robo_immortal`）翻译后塞进
`bot.config["Builds"]`。
⚠️ **spike 点**：ares 的 `config` 何时可写、`BuildOrderRunner` 在 `main.py:332`
（`on_start` 内）就构造了 —— 注入必须在那之前，或注入后重新触发
`configure_opening_from_yml_file`。实现者确认时序。

### 4.3 set_build 真实现
```python
def set_build(self, build_name: str) -> None:
    # build_name = vibecraft strategy id，已在 4.2 注入 config["Builds"]
    self.bot.build_order_runner.switch_opening(build_name)
```

### 4.4 初始 opening
`BuildOrderRunner` 构造要 `chosen_opening`。bot 启动时给个默认（比如第一个剧本，
或一个空 opening）。玩家之后用语音切。

## 5. 范围边界

- **M1.5 只接 `opening_build` kind 的剧本**（`1g_robo_immortal`）。vibecraft 的
  `midgame_stance` / `lategame_doctrine` ares build runner **管不了**（它一个
  opening 跑完 `build_completed=True` 就停）。midgame/lategame 接 ares 是 M2+
  的事（可能走 ares 的别的机制或 vibecraft 自己的 production override）。
- M1.5 出口（设计文档 §12）：手机说「切 1门Robo」→ `switch_opening("1g_robo_immortal")`
  → ares 真的按那个 build order 造东西。**真实 SC2 验证留 M1.6 端到端**。

## 6. M1.5 实现者的 spike / 待办

1. ⚠️ **spike A**：ares step 里 protoss 的 supply/gas/expand —— 用语义命令
   （`supply`/`gas`/`expand`）还是直接结构名（`pylon`/`assimilator`/`nexus`）？
   读 `_parse_string_command` 全文 + 试一条。
2. ⚠️ **spike B**：`bot.config` 注入时序 —— `BuildOrderRunner` 在 `on_start`
   里就构造（`main.py:332`）。注入 `config["Builds"]` 要赶在它之前，或注入后调
   `build_order_runner.configure_opening_from_yml_file()` 重新加载。
3. step 翻译映射表（§3）实现成函数 + 单测（每条 vibecraft step 类型一个用例）。
4. verb/object → ares 名的映射：建筑/单位用小写名应该通用，但要核对 ares 认的
   是 `UnitTypeId` 名还是别的（`build_order_parser.py` 的 `_parse_string_command`
   全文会说明）。
5. `@chrono` 等 modifier：M1.5 至少处理 `@chrono`（插一条 ares `chrono` step）。
   其它 modifier 若 vibecraft 剧本里没用到可暂不管。
6. 单测策略：翻译层是纯函数，**完全可单测**（vibecraft 剧本 dict → ares dict，
   无需 ares/SC2）。`set_build` → `switch_opening` 的对接用 mock bot 测。真实
   ares 跑留 M1.6。
7. `ares_adapter.py` 的 `set_build` docstring / 注释里那条错误的「实际 API 在
   ares.build_runner.BuildRunner.set_build」要一并改对。
